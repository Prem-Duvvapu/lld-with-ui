# Build spec — `restaurant` module (backend from scratch + frontend wiring)

Hand this whole file to the implementing agent. It is self-contained: every name, signature,
number and acceptance test is fixed here so no design judgement is required.

Repo: `lld-with-ui`. Java 17 / Spring Boot 3.2 backend on 9090, React 19 / Vite frontend on 3000.
All state is in-memory (`ConcurrentHashMap` + `ReentrantLock`) and resets on restart — deliberate.

**Work on a branch: `feat/restaurant-module`. Never commit to `main`.**
**Never start the servers** (`mvn spring-boot:run`, `npm run dev`, `./start.sh`). Build and test only.

### 2.1 Enums with transition tables

`TableStatus` — `AVAILABLE, RESERVED, OCCUPIED`

| from | allowed next |
|---|---|
| AVAILABLE | RESERVED, OCCUPIED |
| RESERVED | OCCUPIED, AVAILABLE |
| OCCUPIED | AVAILABLE |

`OrderStatus` — `PLACED, PREPARING, READY, SERVED, BILLED, CANCELLED`

| from | allowed next |
|---|---|
| PLACED | PREPARING, CANCELLED |
| PREPARING | READY, CANCELLED |
| READY | SERVED |
| SERVED | BILLED |
| BILLED | *(terminal — empty set)* |
| CANCELLED | *(terminal — empty set)* |

Both enums expose exactly this shape (copy the pattern from `com.lld.uber.model.RideStatus`):

```java
public Set<OrderStatus> allowedNext()          // never null, unmodifiable
public boolean canTransitionTo(OrderStatus to) // false for null
```

Rules that the tests pin: no self-transitions; no backward transitions; terminal states allow
nothing; `allowedNext()` returns an unmodifiable set for every constant.

`MenuCategory` — `APPETIZER, MAIN, DESSERT, BEVERAGE`
`PaymentMethod` — `CASH, CARD, UPI`
`PaymentStatus` — `SUCCESS, FAILED`
`StaffRole` — `WAITER, CHEF`

### 2.2 Id formats (tests assert these exactly)

- Order: `ORD-00001`, zero-padded to 5, generated by an `AtomicLong`
- Bill: `BILL-00001`
- Payment: `PAY-00001`
- Menu item: `M-001`
- Table: `T1`..`T6` (seeded, not generated)

### 2.3 Billing Strategy — fixed arithmetic

```java
public interface BillingStrategy {
    String getName();
    BillBreakdown compute(double subtotal);
}
public record BillBreakdown(double subtotal, double discount, double tax,
                            double serviceCharge, double total) {}
```

Computation, in this order, every value rounded to 2 decimals (`Math.round(x * 100.0) / 100.0`):

```
discount      = subtotal * discountRate
taxable       = subtotal - discount
tax           = taxable * 0.05
serviceCharge = taxable * 0.10
total         = taxable + tax + serviceCharge
```

| Strategy | `getName()` | discountRate |
|---|---|---|
| `StandardBillingStrategy` | `"STANDARD"` | 0.00 |
| `HappyHourBillingStrategy` | `"HAPPY_HOUR_20%"` | 0.20 |

`BillingStrategyFactory.forTime(LocalTime t)` returns HappyHour when the hour is **16, 17 or 18**
(i.e. 16:00:00–18:59:59 inclusive), Standard otherwise. Boundaries are part of the test.

**Worked examples the tests assert:**
- subtotal `1000.00` → STANDARD: discount `0.00`, tax `50.00`, service `100.00`, total `1150.00`
- subtotal `1000.00` → HAPPY_HOUR: discount `200.00`, tax `40.00`, service `80.00`, total `920.00`
- subtotal `0.00` → total `0.00` under both

## 3. Services

### 3.1 `TableAllocationService` — THE CONCURRENCY POINT. Read this twice.

Two waiters seating parties must never both get the same table. The naive version is a
**check-then-act race**:

```java
// WRONG — do not write this
if (table.getStatus() == TableStatus.AVAILABLE) {
    table.setStatus(TableStatus.OCCUPIED);   // another thread can land between the two lines
}
```

`ConcurrentHashMap` makes each `get` and each `put` atomic. It **cannot** make a
read-decide-write *sequence* atomic. Required implementation:

```java
private final ConcurrentMap<String, ReentrantLock> tableLocks = new ConcurrentHashMap<>();
private ReentrantLock lockFor(String tableId) {
    return tableLocks.computeIfAbsent(tableId, k -> new ReentrantLock());
}
```

`occupy(String tableId, int partySize)` acquires that table's lock and holds it across the whole
check-and-write. Per-table locks, never one global lock — two different tables must be seatable in
parallel, and a test asserts exactly that.

Methods:
- `RestaurantTable occupy(String tableId, int partySize)` — throws `TableNotFoundException` if unknown,
  `TableUnavailableException` if not AVAILABLE/RESERVED, or if `partySize > capacity`.
- `void release(String tableId)` — back to AVAILABLE; null-safe, silently ignores an unknown id.
- `List<RestaurantTable> findAvailable(int partySize)` — AVAILABLE tables with `capacity >= partySize`,
  smallest capacity first (best fit).

### 3.2 `RestaurantService` — the facade the controller delegates to wholesale

```java
List<RestaurantTable> getTables()
List<MenuItem> getMenu()
RestaurantTable seatGuests(String tableId, int partySize)
Order placeOrder(String tableId, String waiterName, List<OrderLineRequest> lines, String notes)
Order getOrder(String orderId)
List<Order> getOrders()
Order cancelOrder(String orderId)
Bill generateBill(String orderId)          // order must be SERVED; moves it to BILLED
Payment payBill(String billId, PaymentMethod method)  // marks paid, releases the table
List<Order> getOrdersForTable(String tableId)
```

Rules:
- `placeOrder` requires the table to be OCCUPIED, the line list non-empty, every menu item to exist
  and be `available`, and every quantity `>= 1`. Order starts `PLACED`.
- Every status change goes through `OrderStatus.canTransitionTo` and throws
  `InvalidOrderTransitionException` when rejected. No `setStatus` bypass anywhere.
- `generateBill` computes the subtotal from the order lines, picks the strategy via
  `BillingStrategyFactory.forTime(LocalTime.now())`, and stores the breakdown on the `Bill`.
- `payBill` throws `BillAlreadyPaidException` on a second call; on success sets `PaymentStatus.SUCCESS`,
  marks the bill paid, and calls `TableAllocationService.release(...)`.

### 3.3 `KitchenService`

```java
List<Order> pendingOrders()              // status PLACED or PREPARING, oldest createdAt first
Order startPreparation(String orderId)   // PLACED -> PREPARING
Order markReady(String orderId)          // PREPARING -> READY
Order markServed(String orderId)         // READY -> SERVED
```

### 5.1 Isolated `/sim/*` endpoint set — required

The simulation must not be able to corrupt the live data. Follow `SplitwiseService` exactly: the
service holds **a second repository instance** (`private final RestaurantRepository simRepository =
new RestaurantRepository();`) plus `private final List<RestaurantEvent> simEventLog =
new CopyOnWriteArrayList<>();`, and a parallel set of `sim*` methods that touch only those.

| Method | Path |
|---|---|
| POST | `/sim/reset` — reseed the sandbox, clear the event log |
| GET | `/sim/state` — `{ tables, orders, bills }` |
| POST | `/sim/seat` |
| POST | `/sim/order` |
| POST | `/sim/prepare` |
| POST | `/sim/ready` |
| POST | `/sim/serve` |
| POST | `/sim/bill` |

| GET | `/sim/events` |

`RestaurantEvent` is a model record: `id (long), type (String), actor (String), message (String),

## 7. Two mandatory edits to existing shared tests

These are guard-rails, not obstacles. Skipping them turns the build red.

1. **`backend/src/test/java/com/lld/config/DomainExceptionContractTest.java`** — add
   `"RestaurantException"` to the existing `BASES` set. It is a module base carrying the hierarchy,
   like `AirlineException` and `UberException`; bases are never thrown directly, so they carry no
   `@ResponseStatus`. Without this, `everyConcreteExceptionDeclaresAStatus` fails.

2. **`backend/src/test/java/com/lld/config/GlobalExceptionHandlerTest.java`** — add one
   `arguments(...)` row per new concrete exception to the `domainExceptions()` `@MethodSource`,
   with its expected status. That test maps every exception→status explicitly by design.

## 8. Tests — four flavours, `backend/src/test/java/com/lld/restaurant/`

Model them on `com.lld.uber.*Test`, which are the reference.

**`RestaurantServiceTest`** (~25 tests) — the lifecycle end to end; seating a too-small table;
ordering against an AVAILABLE table rejected; unknown/unavailable menu item; quantity 0 rejected;
cancel legal from PLACED and PREPARING, rejected from SERVED; bill only from SERVED; double-pay
rejected; table released to AVAILABLE after payment; order history scoped per table.

**`BillingStrategyTest`** (~12 tests) — the arithmetic in section 2.3 pinned exactly, both
strategies, zero subtotal, rounding to paise, `forTime` boundaries at 15:59, 16:00, 18:59, 19:00,
and the two `getName()` strings.

**`OrderStatusTest`** (~12 tests) — the transition table above, exhaustively. Include a
`@ParameterizedTest @EnumSource` asserting every constant declares a non-null set and rejects
`null`, no self-transitions, and that `allowedNext()` is unmodifiable.

**`RestaurantConcurrencyTest`** (~6 tests) — `CountDownLatch` start/done, bounded
`await(5, TimeUnit.SECONDS)`, assert invariants not timings:
- `twoWaitersRacingForOneTable_onlyOneWins` — 2 threads, 1 table, exactly 1 success.
- `twentyWaitersOneTable_nineteenRejected`.
- `disjointTablesAllSucceed` — 6 threads on 6 different tables, **all 6 must win** (proves the locks
  are per-table and don't serialise unrelated work).
- `repeatedRaceNeverProducesTwoWinners` — the same 2-thread race **300 times** with a fresh
  repository each round.
- `releasedTableCanBeReclaimedOnce`.
- `concurrentOrdersAllPersist` — no lost writes, no duplicate order ids.

### 8.1 Verify the race test actually detects the race — this step is not optional

A concurrency test that passes against broken code is worse than no test. To verify:

1. Temporarily comment out the `lock.lock()` / `unlock()` in `TableAllocationService.occupy`.
2. **Insert `Thread.sleep(2)` BETWEEN the status check and the status write** — not before the
   check. This is the mistake that produced a false negative on the Uber module: the unguarded
   window is only nanoseconds wide, so a delay placed before the check widens nothing and the suite
   passes against genuinely broken code.
3. Run `mvn test -Dtest=RestaurantConcurrencyTest`. It **must go red**. If it stays green the test
   is worthless — fix the test, not the assertion.
4. Restore the file exactly (`git checkout -- <file>`) and confirm green again.

Report what you saw at step 3. If you cannot make it fail, say so explicitly rather than claiming
verification.

## 10. Known trap

A single hard `javac` error aborts Lombok's annotation processing, which produces a flood of
spurious "cannot find symbol" errors on generated getters and setters in unrelated files.
**Fix the first real error and the rest disappear** — do not chase them individually.
